# 直播-Windows 桌面版 功能卡片

> 模板：Spec-Lite v1.0 修订版。

## 1. 📌 功能描述（阶段 0 创建时填写）

- **一句话概述**：为已有的电视直播 APK 补一个 Windows 桌面程序——双击弹出应用自己的窗口（原生窗口壳 + 内嵌 WebView2），窗口内是频道列表和播放页，不开浏览器、不装 JDK / mpv / VLC。

- **用户与场景**：
  - 主场景：在 Windows 电脑上想看同样的电视频道，双击 `电视直播.exe` 弹出程序窗口，点台即播；关掉窗口就退出，不留后台常驻进程。
  - 兜底：内置源失效时，在窗口里填自己的 m3u/txt 订阅地址，立刻换源；随时可一键恢复内置源。
  - 只在本机用，不需要给局域网其他设备提供服务。

- **验收条件**：
  - **AC-1 一键启动**：双击 `电视直播.exe`（或源码版 `启动.bat`）后，≤15 秒内弹出应用自身窗口并展示频道列表；全程不出现浏览器、不出现命令行黑框、无需手动输入地址。
  - **AC-2 开箱可看**：首次运行且无用户配置时，直接复用 `app/src/main/res/raw/channels.txt`（441 条记录，去重后 **440 台**、11 个分组）作为内置源；点击任一频道，≤5 秒内出画面并出声音。
  - **AC-3 分组切换**：页面展示全部分组及各自台数，点击分组后列表只显示该组频道，切换响应 ≤200 ms。
  - **AC-4 自定义订阅源**：窗口内有「订阅源」入口，输入 http/https 地址并保存后频道列表立即切换为该源内容；重新打开程序仍生效（持久化到本地配置文件）。
  - **AC-5 恢复默认源**：提供「恢复默认源」按钮，点击后清空自定义源并重新加载内置 440 台，给出"已恢复默认源"提示。
  - **AC-6 播放失败可诊断**：频道流不可达 / 源解析出 0 个频道 / 地址格式非法时，界面给出明确中文提示，不白屏、不静默失败；对浏览器内核无法播放的协议（rtmp/rtsp）明确提示"该协议浏览器不支持"。
  - **AC-7 仅本机监听**：后台服务只绑定 `127.0.0.1`，同一局域网其他设备访问本机 IP 时连接被拒绝；不提供任何无需鉴权的局域网写接口。
  - **AC-8 单文件窗口版 exe**：用 PyInstaller 打成单个 exe 且无控制台窗口，在未装 Python 的 Windows 上双击即出窗口；窗口关闭后进程退出、本地服务随之停止。

- **不做的事**（防范围蔓延）：
  - 不做 EPG 节目单（不接 `epg.51zmt.top` 的 XMLTV）
  - 不改动 `app/` 下的 Android 代码，不重新打 APK
  - 不做录制、回看、点播、搜索、Xtream/Stalker 门户
  - 不引入前端框架（不用 React/Vue），界面用原生 HTML + CSS + JS
  - 不重写播放器内核，HLS 播放仍由 hls.js 承担
  - 不支持 RTMP/RTSP/组播协议，只做明确提示
  - 不解码作者私有的 AES 十六进制源格式（内置源与常规 m3u/txt 不受影响）
  - 不做多用户、多窗口、局域网共享、系统托盘常驻
  - 不在应用内自动更新、不连任何第三方服务端

- **验证方式**：
  - 单元测试：`python -m pytest tests/ -v`（69 项）
  - 集成测试：进程内起服务，用 `urllib` 请求 `/api/channels` 断言 440 台 / 11 组；请求 `/api/proxy` 断言 m3u8 重写与二进制透传。
  - 界面验证：Chrome 无头渲染真实页面，断言 440 个频道卡片、源徽标与分组台数。
  - 播放验证：真实浏览器内用 hls.js 经代理拉流，断言 `MANIFEST_PARSED` 与 `FRAG_LOADED`。
  - 打包验证：`python build.py` 后双击 `dist/电视直播.exe`，断言窗口标题出现且接口返回 440 台。

- **外部副作用**（逐项待授权，未授权不执行）：
  - [x] 联网下载 hls.js 1.5.17（404 KB）到 `win/static/vendor/`
  - [x] `pip install pyinstaller`（6.22.3，仅构建时需要）
  - [x] `pip install pywebview`（6.2.1，窗口外壳；运行时依赖系统 WebView2）
  - [x] 运行时访问外部直播源（功能本身）

- **已知风险**：
  - 频道流来自第三方，随时可能失效；能播多少台取决于源当天状态。
  - 部分源分片下载本身就要 30 秒以上（实测 5.3 MB / 38 秒），这类源即使能连上也会卡顿。
  - 单文件 exe 首次启动需解压自身并初始化 WebView2，冷启动 5~10 秒。
  - 依赖系统 WebView2 运行时；Win11 与打过补丁的 Win10 自带，极老系统需装 Evergreen Runtime。

## 3. 🧠 技术方案（开发过程中更新）

### 选型

| 选择 | 理由 |
|---|---|
| Python 3 + 标准库 `http.server` | 后台零第三方运行时依赖，服务层可独立测试 |
| **pywebview + 系统 WebView2 做窗口壳** | 直接得到一个原生窗口（有标题栏、任务栏图标、独立进程），却不用重写界面和播放器；exe 仅 13.3 MB。不选 Electron（100 MB 起）、不选 Compose Desktop（需 JDK + 300 MB 依赖） |
| 界面用原生 HTML/CSS/JS + hls.js | 避免前端构建链；hls.js 是浏览器播 HLS 的事实标准，404 KB 本地内置保证离线可用 |
| 后台起本地服务而非纯静态页 | 浏览器内核的 CORS 禁止页面读取第三方直播源，必须由本机代理转发 |

### 架构

```
电视直播.exe（原生窗口，pywebview / WebView2）
   │  窗口内加载 http://127.0.0.1:8899/
   ↓
本地服务（仅 127.0.0.1，随窗口启停）
   ├── GET /                → static/index.html
   ├── GET /api/channels    → SourceManager.current() → 440 台
   ├── POST /api/source     → 下载校验 → 落盘 → 切换
   ├── POST /api/source/reset
   └── GET /api/proxy?u=... → proxy.fetch() → 若是 m3u8 则重写地址后返回
                                   │
                                   └── 上游直播源
```

分层：`channels`（纯解析） ← `sources`（源生命周期） ← `server`（HTTP） ← `app`（后台生命周期） ← `desktop`（窗口）。`proxy` 与 `channels` 互不依赖，可独立测试。

### 关键决策

| 决策 | 原因（均有实测依据） |
|---|---|
| 窗口壳用 pywebview + WebView2，而不是重写原生界面 | 界面与播放器逻辑已跑通并被验证过，换壳只动入口，一天内可交付；重写为 Compose/libVLC 需 2~3 周且要装 JDK |
| 窗口版同时保留浏览器模式入口 `app.py` | 开发调试方便；WebView2 缺失的机器仍可用浏览器兜底 |
| 窗口版用 `--windowed` 打包，错误一律弹 `MessageBoxW` | 无控制台时异常会静默吞掉，用户只看到程序一闪而过 |
| 后台服务线程设为 daemon，窗口关闭即退出 | 桌面程序关窗就该结束，不能留后台常驻进程 |
| 默认**不发送 Referer**，仅在上游返回 401/403/404 时补一次同源 Referer 重试 | 实测内置源中 `gmxw.7766.org` 带 Referer 返回 404、不带返回 200 |
| 代理超时 30 秒、hls.js 分片超时 45 秒 | 实测某分片 5.3 MB 需 38 秒，按 15 秒超时会全部误判失败 |
| 只绑 `127.0.0.1` + 校验 Host 头 | 与 Android 版被移除的无鉴权 34567 服务不同，这里不接受任何局域网访问，也防 DNS rebinding |
| 允许代理局域网地址，但禁止代理回本服务自身端口 | 部分源在内网；禁止自指可防本服务被当作跳板 |
| 数据目录优先程序目录，不可写则退 `%LOCALAPPDATA%` | 便携版保持配置随手带；exe 放在 Program Files 时仍可运行 |
| m3u8 内所有 URI 一律改写（分片、子列表、`EXT-X-KEY`/`MAP`/`MEDIA`） | 漏改任一类都会导致加密流或主播放列表播不出来 |
