# 跨端播放踩坑记录

> 同一批直播源，在 Windows（WebView2 + hls.js）和电视（Android Media3/ExoPlayer）两端会踩到**同一类坑**。
> 规则：每修完一个播放问题，先在这里登记，再回头检查另一端有没有同样的问题。

---

## P-1 「准备完成」不等于「能看到画面」

**现象**：点一个台后一直转圈，或状态显示「正在播放/直播中」但画面永远黑屏，用户以为程序死机。

**根因**：把播放器的「拿到播放列表」或「能开始播放」当成了成功信号。慢源在这两个信号之后，可能还要几十秒才有第一帧。

**实测证据（Windows 端）**：

| 频道 | 播放列表 | 12 秒内下的分片 | 结论 |
|---|---|---|---|
| CCTV5 | 225 ms 到手 | 0 个 | 列表成功 ≠ 能看 |
| CCTV13 | 207 ms | 470 ms 下完，时间轴 12.1s→14.1s | 真能看 |

单分片 5068 KB / 51.97 秒（独立测速），播放器必须等它下完才有画面。

**正确判据是「首帧真正渲染」**：

- Windows / hls.js：`video` 的 `playing` 事件（**不是** `MANIFEST_PARSED`）
- 电视 / Media3：`Player.Listener.onRenderedFirstFrame()`（**不是** `onIsPlayingChanged`，也不是 `STATE_READY`）

`isPlaying` 和 `STATE_READY` 只代表「缓冲够了，可以开始播」，此时画面仍在解码/排队。

> 注：电视版 `PlayerType.WEBVIEW` 分支的成功信号来自网页自己 `console.log("success")`，语义由页面决定，本次未纳入改造范围；若后续有余力，应让页面在 `video.playing` 时才上报。

## P-2 没有超时兜底，慢源永远转圈

**现象**：不报错、不结束、不提示，只有一个转圈。

**根因**：慢源既不抛错误也不出画面，只会一直停在缓冲态。没有看门狗，就没有任何结束条件。

**正确做法**：换台/换源后启动首帧看门狗（20 秒）：

1. 超时 → 切备用线路，**最多 2 次**
2. 仍无首帧 → 给明确中文提示（「源太慢或已失效，请换台」）并停止无效重试
3. 若已 `isPlaying && STATE_READY`（音频先行但画面慢）→ 不干预，避免误杀

---

## P-3 编码不支持被静默忽略

**现象**：某些台（如湖南卫视）永远播不出来，且没有任何提示。

**根因**：

- Windows：hls.js 不支持 TS 容器里的 H.265，报 `fragParsingError: Unsupported HEVC in M2TS`
- 电视：ExoPlayer 抛解码类错误码，但原错误处理只认网络/容器错误，其余直接 `return` 丢弃

**正确做法**：按错误码分类，给用户看得懂的文案：

| 错误码 | 含义 | 给用户的文案 |
|---|---|---|
| `ERROR_CODE_DECODING_FORMAT_UNSUPPORTED` (4005) | 编码不支持 | 该频道的视频编码当前设备不支持，请换台 |
| `ERROR_CODE_DECODING_FORMAT_EXCEEDS_CAPABILITIES` (4004) | 超出设备能力 | 同上 |
| `ERROR_CODE_DECODING_FAILED` (4003) | 解码失败 | 同上 |
| `ERROR_CODE_PARSING_CONTAINER_UNSUPPORTED` (3003) | 容器/编码不支持 | 同上 |
| `ERROR_CODE_IO_NETWORK_CONNECTION_TIMEOUT` (2002) | 连不上/超时 | 源太慢或已失效 |
| `ERROR_CODE_IO_NETWORK_CONNECTION_FAILED` (2001) | 连接失败 | 同上 |

换线路对编码问题无效，所以这类错误应该**直接提示**，不要走重试链。

---

## P-4 关掉「自动切源」时，把错误也一起吞了

**现象**：设置里关闭自动切源后，坏源没有任何提示，纯黑屏转圈。

**根因**：代码写成 `if (!autoSwitchSource) return`，位置在所有提示逻辑之前。

**正确做法**：「要不要自动换线路」和「要不要告诉用户原因」是两件事。前者受配置控制，后者必须永远执行。

---

## P-5 记不住重试计数导致无限循环

**现象**：超时后不断换线，永远不收敛。

**根因**：换线路的入口（`switchSource`）里顺手把首帧重试计数也清零了，于是「超时→换线→计数归零→再超时」死循环。

**正确做法**：重置要分两种语义——「换频道」才清零计数，「换线路」必须保留计数。

---

## P-6 源质量本身（不是程序 bug）

2026-10-29 抽样 40 个 HLS 台：

| 结果 | 数量 |
|---|---|
| H.264，理论可播 | 22 |
| 超时（源太慢） | 9 |
| HTTP 错误（源挂了） | 6 |
| 未识别容器 | 2 |
| 仅 H.265 | 1 |

央视 + 卫视力测：

- **流畅**：CCTV13、浙江卫视、东方卫视、河南卫视、内蒙古卫视
- **很慢**：黑龙江卫视、江西卫视（首分片 > 5 秒）
- **打不开**：CCTV5、CCTV8、CCTV12、CCTV15、CCTV16、深圳卫视、安徽卫视、辽宁卫视、吉林卫视
- **H.265 无解（网页内核）**：湖南卫视

结论：不要把「点台播不出来」一律当成程序 bug，先分清是**源**、**编码**还是**播放器判定**的问题。诊断顺序：

1. 播放列表能不能拿到？（能 → 不是网络/DNS 问题）
2. 第一个分片能不能拿到？多大？多久？（慢 → 源带宽问题）
3. 报的是什么错？（`fragParsingError/HEVC` → 编码问题，重试无用）

## 新端接入检查清单

任何新增播放端（Web、桌面、移动、TV）都必须满足：

- [ ] 成功判据是**首帧渲染**，不是 manifest/READY/isPlaying
- [ ] 有首帧超时（建议 20 秒），超时先换线（有限次）再报错
- [ ] 错误分类给用户**可见的中文文案**：编码不支持 / 源无响应 / 列表打不开
- [ ] 任何「忽略错误」的分支都确认过：用户仍能看到原因
- [ ] 换线路不清零重试计数
- [ ] 慢源不会让界面无限转圈
